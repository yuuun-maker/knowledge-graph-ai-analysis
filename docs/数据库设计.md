# 数据库设计说明

> 本文档汇总系统当前的数据存储设计，来源为代码与运行库实际定义：关系型数据见 `backend/app/core/sql_database.py`（建表 `_SCHEMA_SQL` + 幂等迁移 `_migrate()`），图数据见 `backend/app/core/database.py`。
>
> **最后校验：2026-10-08**（对照 `backend/data/app.db` 与运行中的 Neo4j 逐表 / 逐属性核对；含课程中心、题库、**L2 一题多知识点**、**L2 阶段 E 向量 BLOB**、**管理员端与审计日志**、**文档级知识融合**）
>
> 系统采用**双存储**：SQLite（关系型，存用户/课程/成员/文档/学习记录/题库/向量/平台治理与审计/**知识融合映射**）+ Neo4j（图，存知识点与关系）。

---

## 一、存储架构

| 存储 | 类型 | 存什么 | 落地文件/模块 |
|------|------|--------|---------------|
| SQLite | 关系型 | 用户与资料、课程与成员、文档、学习记录、收藏、知识点向量、题库、**平台治理与审计日志**、**知识融合候选与映射** | `backend/app/core/sql_database.py` |
| Neo4j | 图数据库 | `KnowledgePoint` 节点 + 四类关系 | `backend/app/core/database.py` |

- `course_id` 三端统一为**整数**：SQLite 自增整数 → Neo4j 存整数属性 → API 传整数。
- `t_learning_record.kp_id` / `t_student_favorite.kp_id` / `t_question.kp_id` / `t_question_kp.kp_id` 均为**逻辑外键**，指向 Neo4j 的 `KnowledgePoint`，不建物理外键（跨库无法建）。
- **L2 一题多知识点（2026-09-22）**：`t_question_kp` 是题目-知识点关联的**权威数据**（一题可挂 N 个 kp），`t_question.kp_id` 退化为它的**主知识点冗余投影**——两者由 `SQLDatabase.set_question_kps()` 同事务维护，因此读侧（前端 / 统计 / 兼容期调用方）看到的 `kp_id` 语义不变。详见 2.10 / 2.15。
- 第一阶段用 SQLite（零部署、Python 标准库）；第二阶段迁移 MySQL 仅替换 `sql_database.py` 底层连接实现，表名、字段名、方法签名保持不变，业务代码零改动。
- 新增列一律走 `_migrate()` 的 `ALTER TABLE`（不写进 `CREATE TABLE`），以保证「新建库」与「迁移库」表结构不分叉——详见第七章。

## 二、SQLite 关系型表（22 张）

按领域分组：用户与资料（2.1–2.2）、课程与成员（2.3–2.5）、文档（2.6）、学习数据（2.7–2.9）、题库（2.10–2.12、**2.15**）、向量与缓存（2.13–2.14）、**知识融合（2.16–2.20）**、**平台治理与审计（2.21）**、级联清理（2.22）。

> 表数量以 `_SCHEMA_SQL` 实数（**22 张**，2026-10-08 核对）为准。其中 `t_question_import_batch`（Scope D 导入批次）尚未在此单列字段明细，字段定义见 `backend/app/core/sql_database.py` 与 [题库功能说明.md](题库功能说明.md)。
>
> **相对 2026-09-23 版新增 6 张表**：管理员端的 `t_admin_audit_log`，以及知识融合的 5 张 `t_kp_fusion_*`。六张全部由 `_SCHEMA_SQL` 的 `CREATE TABLE IF NOT EXISTS` 建出，**不需要 `_migrate_xxx`**（迁移只用于给已有表加列或重建 CHECK）。融合模块的完整设计与评估见 [文档级知识融合与实体消歧实施报告.md](文档级知识融合与实体消歧实施报告.md) §5。

### 2.1 t_user 用户表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| user_id | INTEGER | PK AUTOINCREMENT | 主键 |
| username | TEXT | NOT NULL UNIQUE | 登录名 |
| password_hash | TEXT | NOT NULL | 密码哈希（PBKDF2-SHA256） |
| role | TEXT | NOT NULL DEFAULT 'student'，CHECK ∈ {admin, teacher, student} | 角色（`admin` 为平台管理员，管理员端引入） |
| display_name | TEXT | | 显示名 |
| email | TEXT | | 邮箱 |
| is_active | INTEGER | NOT NULL DEFAULT 1，CHECK ∈ {0, 1} | 是否启用 |
| must_change_password | INTEGER | NOT NULL DEFAULT 0 | 下次登录强制改密；**仅新引导创建的账号与被管理员重置过密码的账号置 1**，历史行一律 0 |
| created_at | TEXT | NOT NULL DEFAULT 本地时间 | 创建时间 |
| updated_at | TEXT | NOT NULL DEFAULT 本地时间 | 更新时间 |

索引：`idx_role (role)`

> 认证相关列（`password_hash` / `username` / `role` / `is_active`）**不随个人中心改动**：扩展资料一律写入 `t_user_profile`。
>
> **`role` 的 CHECK 扩到含 `admin` 必须重建整张表**（`_migrate_admin_role()`）：SQLite 不支持修改 CHECK，与 `_migrate_question_types()` 同理，且因 `t_user` 被 `t_course` / `t_document` / `t_learning_record` 等多表引用，重建要用「关闭外键的独立连接」。`must_change_password` 则是普通列加法（`_migrate_admin_user_columns()`），`PRAGMA table_info` 守卫后 `ALTER TABLE ADD COLUMN`。

> ⚠️ **一处已知的结构分叉**：`must_change_password` 同时写进了 `_SCHEMA_SQL` 的 `CREATE TABLE`（带 `CHECK (must_change_password IN (0, 1))`）**和** `_migrate_admin_user_columns()` 的 `ALTER TABLE`（不带 CHECK）——这与第七章「新增列只写 `_migrate()`、不写 `CREATE TABLE`」的纪律相悖。后果：**新建库该列有 CHECK，旧库迁移来的没有**。取值合法性目前靠应用层兜底，不影响功能，但核对表结构时会看到两库不一致，勿误判为「迁移没跑」。

### 2.3 t_course 课程表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| course_id | INTEGER | PK AUTOINCREMENT | 主键（三端统一的整数） |
| course_code | TEXT | UNIQUE | 课程编号 |
| course_name | TEXT | NOT NULL | 课程名 |
| description | TEXT | | 课程描述 |
| teacher_id | INTEGER | NOT NULL，FK → t_user(user_id) | 创建者（课程归属的唯一依据） |
| status | INTEGER | NOT NULL DEFAULT 1，CHECK ∈ {0, 1} | 状态 |
| created_at | TEXT | NOT NULL DEFAULT 本地时间 | 创建时间 |
| updated_at | TEXT | NOT NULL DEFAULT 本地时间 | 更新时间 |
| join_code | TEXT | 可空；唯一性由独立唯一索引保证 | 8 位加课码 |
| join_mode | TEXT | NOT NULL DEFAULT 'approval'，取值见 `JOIN_MODES` | 加入方式 |
| organization | TEXT | | 院系/机构 |
| category | TEXT | | 课程分类 |
| cover | TEXT | | 封面 |
| is_public | INTEGER | NOT NULL DEFAULT 1 | 是否公开（可被「发现课程」搜索到） |
| governance_status | TEXT | NOT NULL DEFAULT 'normal'；取值见 `COURSE_GOVERNANCE_STATUS` | **平台治理状态**：`normal` / `hidden`（平台下架）/ `archived`（归档） |
| governance_note | TEXT | | 治理操作备注（管理员填写） |
| archived_at | TEXT | 可空 | 归档时间 |

索引：`idx_teacher_id (teacher_id)`、`uq_course_join_code`（**UNIQUE**，仅 `join_code`）

> `join_code` 等 6 列由 `_migrate_course_center()` 补入，**刻意不写进 `CREATE TABLE`**（见第七章）。`join_code` 只加成普通可空列——SQLite 的 `ALTER TABLE ADD COLUMN` 不允许带 UNIQUE，唯一性交给独立的 `CREATE UNIQUE INDEX`（唯一索引允许多个 NULL，可与历史未发码的行共存）。
>
> `governance_status` / `governance_note` / `archived_at` 三列由 `_migrate_admin()` 补入，同样**不写进 `CREATE TABLE`**（新库也走这段迁移），且**不带 CHECK**——取值合法性由应用层 `COURSE_GOVERNANCE_STATUS` 白名单兜底。历史课程一律 `normal`。
>
> **治理状态与业务状态是两回事，别混用**：`status`（0/1）是**教师维度**的业务开关，`governance_status` 是**平台维度**的下架/归档。管理员「下架课程」只改 `governance_status='hidden'`，**不动 `status`**；「代教师关闭课程」才改 `status=0`。对外可见性统一走 `COURSE_VISIBLE_SQL = "status = 1 AND COALESCE(governance_status, 'normal') = 'normal'"`——`COALESCE` 是为了兼容 `governance_status` 尚未回填的历史行。

### 2.4 t_course_member 课程成员表

用户 ↔ 课程的多对多关系表，**替代「把学生硬编码进课程表」的做法**。教师与学生在同一张表内，用 `role` 区分。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| member_id | INTEGER | PK AUTOINCREMENT | 主键 |
| course_id | INTEGER | NOT NULL，FK → t_course(course_id) | 课程 |
| user_id | INTEGER | NOT NULL，FK → t_user(user_id) | 用户 |
| role | TEXT | NOT NULL DEFAULT 'student'，CHECK ∈ {teacher, student} | 课程内角色 |
| status | TEXT | NOT NULL DEFAULT 'pending'，CHECK ∈ {pending, approved, rejected, removed} | 成员状态 |
| join_source | TEXT | NOT NULL DEFAULT 'code'，CHECK ∈ {create, code, invite, apply, import} | 加入来源 |
| applied_reason | TEXT | | 申请理由（发现课程页申请时填写） |
| reviewed_by | INTEGER | 可空 | 审核人（教师） |
| reviewed_at | TEXT | 可空 | 审核时间 |
| review_comment | TEXT | 可空 | 审核意见 |
| joined_at | TEXT | 可空 | 正式加入时间（approved 时才写入） |
| created_at / updated_at | TEXT | NOT NULL DEFAULT 本地时间 | 时间戳 |

约束：`UNIQUE (course_id, user_id)`——同一用户在同一课程至多一条关系，重复加入不产生脏数据
索引：`idx_cm_course_status (course_id, status)`、`idx_cm_course_role (course_id, role)`、`idx_cm_user_status (user_id, status)`

> **状态语义**：只有 `status='approved'` 才视为课程成员并放行**内容访问**（文档/图谱/问答/学习路径）；`pending` / `rejected` / `removed` 仅有**元数据级**读取权，用于查看自己的申请状态，访问内容一律 4003。被移除的学生再次用加课码加入时，服务层强制回落为 `pending`，不因 `join_mode='auto'` 自动放行——避免泄露出去的加课码撤销教师的「移除」决定。
>
> 教师创建课程时自动写入 `role='teacher', status='approved', join_source='create'`。

### 2.6 t_document 文档表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| doc_id | INTEGER | PK AUTOINCREMENT | 主键 |
| course_id | INTEGER | NOT NULL，FK → t_course(course_id) | 所属课程 |
| uploader_id | INTEGER | NOT NULL，FK → t_user(user_id) | 上传者 |
| file_name | TEXT | NOT NULL | 文件名 |
| file_type | TEXT | NOT NULL，CHECK ∈ {PDF, TXT, DOCX, MD} | 文件类型 |
| file_size | INTEGER | NOT NULL | 文件大小 |
| file_sha256 | TEXT | | 文件哈希 |
| file_path | TEXT | | 存储路径 |
| parse_status | TEXT | NOT NULL DEFAULT 'UPLOADED'，CHECK ∈ {UPLOADED, PARSING, PARSED, FAILED} | 解析状态 |
| extract_status | TEXT | NOT NULL DEFAULT 'PENDING'，CHECK ∈ {PENDING, EXTRACTING, COMPLETED, FAILED} | 抽取状态 |
| error_message | TEXT | | 错误信息 |
| chunk_count | INTEGER | NOT NULL DEFAULT 0 | 分块数 |
| entity_count | INTEGER | NOT NULL DEFAULT 0 | 抽取实体数 |
| relation_count | INTEGER | NOT NULL DEFAULT 0 | 抽取关系数 |
| vector_collection | TEXT | | 向量集合名 |
| extract_started_at | TEXT | 可空 | 抽取任务**开始**时刻（旧库历史行为 `NULL`） |
| extract_finished_at | TEXT | 可空 | 抽取任务**结束**时刻（旧库历史行为 `NULL`） |
| created_at | TEXT | NOT NULL DEFAULT 本地时间 | 创建时间 |
| updated_at | TEXT | NOT NULL DEFAULT 本地时间 | 更新时间 |

索引：`idx_course_id`、`idx_uploader_id`、`idx_parse_status`、`idx_extract_status`

> **为什么要单独记抽取起止时刻**：管理端「资源管理 → 知识抽取任务」原先用 `created_at` / `updated_at` 算耗时，而 `updated_at` 会被**任何**后续写操作刷新（回填统计、重建图谱、改元数据），于是「耗时」实际变成了「上传至今」——实测有文档显示 48889 分（34 天）。
>
> 两列由 `_migrate_document_extract_timing()` 补入，**不伪造历史值**：`t_document` 从未记录过抽取完成时刻，历史行的真实耗时无法还原，故两列留 `NULL`，前端显示「—」。之后由 `update_document` 在写 `extract_status` 的同一句 `UPDATE` 里打戳。
>
> 与 `must_change_password` 一样，这两列也**同时出现在 `_SCHEMA_SQL` 与 `_migrate()` 两处**（第七章纪律一的例外）；不同的是两处都是**无约束的可空 `TEXT`**，因此**不产生结构分叉**——不像 `must_change_password` 那样一处带 CHECK、一处不带。

### 2.9 t_kp_embedding 知识点向量表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| course_id | INTEGER | PK（复合主键）NOT NULL | 课程 |

### 2.10 t_question 题目表

### 2.15 t_question_kp 题目-知识点关联表（L2：一题多知识点）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| question_id | INTEGER | PK 之一，FK → t_question(question_id) | 题目 |
| kp_id | TEXT | PK 之一 | 逻辑外键 → Neo4j KnowledgePoint |
| score | REAL | 可空 | 标注置信度（`kp_labeler` 自动标注产物） |
| source | TEXT | NOT NULL DEFAULT 'MANUAL'，CHECK ∈ {MANUAL, AI, IMPORT} | 关联来源（与 `QUESTION_SOURCE` 同口径） |
| is_primary | INTEGER | NOT NULL DEFAULT 0，CHECK ∈ {0,1} | 是否「主知识点」 |
| created_at | TEXT | NOT NULL DEFAULT 本地时间 | 建立时间 |

主键：`(question_id, kp_id)`（同题同 kp 天然幂等）

索引：

- `idx_qkp_kp (kp_id)`——按知识点反查题目（出题 / 覆盖率）
- **`uq_qkp_primary`：`UNIQUE (question_id) WHERE is_primary = 1`**（**部分唯一索引**）——「一题最多一个主知识点」由 DB 层保证而非应用层自觉；SQLite 部分索引自 3.8.0 起支持

**写入纪律**：本表是题目-知识点关联的**唯一事实来源**，`t_question.kp_id` 是它的投影（见 2.10）。兼容期内**只有 `SQLDatabase.set_question_kps()` 一个写入口**，它在一个事务里完成「删除旧关联 → 重建新关联 → 同步投影」，并在应用层归一化（去空、去重、保序、`primary` 不在列表时兜底取首项）。`create_question` / `update_question` / `QuestionService.import_commit` 均经它落库；`update_question` **只在调用方显式传入 kp 字段时**才写关联——否则「教师只改难度」会把多 KP 题**塌缩**成单 KP。

**上限**：`question_service.MAX_KP_PER_QUESTION = 10`（防误传超大数组；同时为组卷的「任一命中即占用配额槽」留出上界）。

**迁移**：`_migrate_question_kp()` 只回填「关联表中无任何行」的题——若已有 `is_primary=1` 的行（教师后续编辑产生）再按 `t_question.kp_id` 插一行主 kp，会同时触碰 `uq_qkp_primary` 导致后端启动即崩。详见第七章。

> L2「一题多知识点」的完整设计、语义口径（决策 1/2/3/4）、验证结果与回滚方式见 [题库与推荐系统设计.md](题库与推荐系统设计.md) §13。

### 2.20 t_kp_fusion_scope 融合作用域表（epoch）

每 `(course_id, document_id)` 一行的**融合版本号**，用于判定「向量索引是否还新鲜」。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| course_id / document_id | INTEGER | PK（复合）NOT NULL | 作用域 |
| epoch | INTEGER | NOT NULL DEFAULT 0 | 融合状态版本；每次 apply / revoke **+1**（首次调用即建行，从 1 开始） |
| indexed_epoch | INTEGER | 可空 | 「向量索引已按此 epoch 建好」的水位，供 `ensure_index` 判新鲜度 |
| updated_at | TEXT | NOT NULL DEFAULT 本地时间 | 更新时间 |

主键：`(course_id, document_id)`

> **为什么需要它**：融合生效会改变读图折叠后的 `kp_id` 集合，旧向量随之失效。`apply` / `revoke` 在**同一个 SQLite 事务**内完成「写入映射 → `epoch+1` → 失效向量」，再由 `fusion_scope_mark_indexed()` 在索引重建后抬升 `indexed_epoch`。`epoch != indexed_epoch` 即代表索引过期需重建——这与 §2.9 的懒重建是同一套新鲜度思路，但判据是版本号而非集合比对。
>
> 无记录时 `fusion_scope_get()` 返回 `None`，视为「从未融合过」，是合法的初始态。

### 2.22 级联清理（防孤儿数据）

**SQLite 未开启外键级联**，所有级联删除都在 `SQLDatabase.delete_course()` / 文档删除路径内按「子表 → 主表」顺序显式执行。

| 触发 | 清理范围 | 说明 |
|------|----------|------|
| 删除题目 | 该题的**知识点关联** + 收藏 + 答题记录 → 题目本身 | `t_question_kp` 有物理外键且连接已开 `PRAGMA foreign_keys=ON`，**必须先删关联行**否则抛 FK 错误；已被作答过的题目由服务层降级为软删（`is_active=0`） |
| 删除文档 | 该文档精确挂载的题目 & 其**知识点关联**/收藏/答题记录；**融合 5 表**（run / candidate / map / conflict / scope） | 课程通用题（`document_id IS NULL`）刻意保留。融合数据走 `delete_fusion_by_document(cid, doc_id)`，必须排在 `DELETE FROM t_document` 之前 |
| 删除课程 | 向量、知识点收藏、学习记录、**成员、邀请**、题库全部、文档、**融合 5 表** → 课程本身 | 顺序不可颠倒，否则留下指向已删课程的孤儿行 |

> 成员/邀请的清理在课程中心改造时补入：此前删课会残留 `t_course_member` 行。
> `t_question_kp` 的清理在 L2「一题多知识点」改造时补入，覆盖 4 个删除点：`delete_question` / `delete_course` / `delete_questions_by_course` / `delete_questions_by_document`。
> 融合数据的清理覆盖**两级**：文档级 `delete_fusion_by_document()`（`document_service.py`）、课程级 `delete_fusion_by_course()`（在 `SQLDatabase.delete_course()` 的事务内调用）。

> **融合数据曾漏清课程级（已修复，2026-10-08）**：这 5 张表最初只挂在**文档级**删除路径上——
> `SQLDatabase.delete_course()` 完全没引用它们，且全仓不存在 `delete_fusion_by_course()`。
> 因为它们都没设物理外键（见 §2.16 说明），漏清**不抛错**，只会静默堆积指向已删课程的孤儿行。
>
> **修复内容**：① 新增 `delete_fusion_by_course()`；② 文档级 / 课程级两个删除函数共用类常量
> `_FUSION_TABLES` 清单（此前的重复字面量正是「加表时只挂一处」的温床）；③ 在 `delete_course()`
> 内以 `conn=conn` 调用，并入同一事务，保证「先删融合行、再删 `t_course`」原子生效；
> ④ `CourseService.delete_course()` 返回体补上 `removed_fusion` 分表计数（对齐文档级路径早就有的
> `removed_fusion`）；⑤ 回归测试 `backend/test_fusion_course_delete.py`（18 项，含「对照课程一行不少」的越界检查）。
>
> **教训**：文档级与课程级是**两条独立的代码路径**，新增子表必须各挂一次——只挂文档级，
> 删文档时正常、删课程时静默漏，且因为不报错而极难发现。

## 七、迁移机制（无 Alembic）

项目未引入迁移框架，schema 演进靠 `SQLDatabase.init_tables()` 在**每次后端启动**时执行，全程幂等：

```
init_tables()
├─ 逐条执行 _SCHEMA_SQL                # 全部 CREATE TABLE / CREATE INDEX IF NOT EXISTS（22 张表）
├─ _migrate()
│  ├─ 1) document_id 补列与回填 + idx_kp_emb_scope
│  │                                  # t_learning_record / t_student_favorite / t_kp_embedding
│  ├─ 2) _migrate_question_bank()     # 题库：t_answer_record 批改列 + t_question 导入列
│  ├─ 3) _migrate_question_kp()       # L2：t_question.kp_id → t_question_kp 主知识点回填
│  ├─ 4) _migrate_embeddings_blob()   # L2 阶段 E：向量表补 embedding_blob + 限量回填
│  ├─ 5) _migrate_course_center()     # 课程中心改造（join_code 等 6 列）
│  ├─ 6) _migrate_admin()             # 管理员端：t_course 补治理三列
│  ├─ 7) _migrate_admin_user_columns()        # t_user 补 must_change_password
│  └─ 8) _migrate_document_extract_timing()   # t_document 补抽取起止时刻两列
├─ _migrate_question_types()          # t_question 重建（扩 q_type CHECK；需独立连接）
├─ _migrate_admin_role()              # t_user 重建（扩 role CHECK 含 admin；需独立连接）
└─ _apply_journal_mode()              # 阶段 G：最后切 WAL（库文件已非空才可设 WAL）
```

> **融合的 5 张新表不在此图内**：它们不需要任何迁移步骤，全由 `_SCHEMA_SQL` 的 `CREATE TABLE IF NOT EXISTS` 建出（见 §2.16–2.20）。

`_migrate()` 的各段都是「先探测、再变更」，重复执行结果一致：

1. **`document_id` 补列**：`PRAGMA table_info` 守卫，缺列才 `ALTER TABLE ADD COLUMN`；随后仅回填 `document_id IS NULL` 的行（历史数据「一课程 == 一文档」，可安全映射）。
2. **`_migrate_question_bank()`**：给 `t_answer_record` 补「批改」相关列（`_ANSWER_NEW_COLUMNS`；`grade_status` 默认 `GRADED`，保证历史记录口径不变），并给 `t_question` 补 Scope D 的导入批次/暂存状态列（`_QUESTION_NEW_COLUMNS`）——后者必须**先于** `_migrate_question_types()` 的重建，才能被一起拷过去。
3. **`_migrate_question_kp()`**（L2）：把 `t_question.kp_id` 回填为 `t_question_kp` 的 `is_primary=1` 行。**判据必须是 `NOT EXISTS (SELECT 1 FROM t_question_kp k WHERE k.question_id = q.question_id)`**——只回填「关联表中无任何行」的题；若只靠 `INSERT OR IGNORE`，已有主知识点的题会被再插一行 `is_primary=1`，同时触碰 `uq_qkp_primary` 部分唯一索引，导致**后端每次启动即崩**。
4. **`_migrate_embeddings_blob()`**（L2 阶段 E）：给 `t_kp_embedding` / `t_question_embedding` 补 `embedding_blob BLOB`，并把 `embedding`(JSON) **限量**转成 float32 BLOB（每次启动 ≤ 5000 行）。限量是刻意的：5 万条 JSON 全量解析约 18 秒，会拖慢启动；重复启动幂等续跑，`backfill_embedding_blobs()` 可显式全量执行。
5. **`_migrate_course_center()` 四步**：
   - `PRAGMA table_info(t_course)` 守卫，逐个补 `_COURSE_NEW_COLUMNS` 中的 6 列；
   - `CREATE UNIQUE INDEX IF NOT EXISTS uq_course_join_code`；
   - 仅为 `join_code IS NULL` 的课程生成加课码（冲突重试至多 20 次）——**教师已发出的码不会被重新生成**；
   - `INSERT OR IGNORE INTO t_course_member ... SELECT ... FROM t_course`，把每门已有课程的 `teacher_id` 变成 `role='teacher'/status='approved'` 成员。靠 `UNIQUE(course_id, user_id)` 保证幂等，且不覆盖教师后续手动改动过的成员行。
6. **`_migrate_admin()`**（管理员端）：给 `t_course` 补 `governance_status` / `governance_note` / `archived_at` 三列（`PRAGMA table_info` 守卫），历史课程一律 `normal`。**同样不写进 `_SCHEMA_SQL`**——新库也走这段迁移，因此两库结构一致，且三列都不带 CHECK，取值由应用层 `COURSE_GOVERNANCE_STATUS` 白名单兜底。
7. **`_migrate_admin_user_columns()`**：给 `t_user` 补 `must_change_password`（`DEFAULT 0`）。历史行取 0 是刻意的——若取 1，一次升级会把所有在线用户挡在改密页上；该标记只对**新引导创建**的账号以及**被管理员重置过密码**的账号置 1。
8. **`_migrate_document_extract_timing()`**：给 `t_document` 补 `extract_started_at` / `extract_finished_at`（均可空 `TEXT`，**不伪造历史值**，旧行留 `NULL`），修复「用 `updated_at` 算抽取耗时」导致显示 48889 分的问题。详见 §2.6。

**四条重要约束**：

- 新增列**只写 `_migrate()`、不写 `CREATE TABLE`**。若两边都写，新建库与迁移库的表结构会分叉（列顺序、默认值不一致）。
- SQLite 的 `ALTER TABLE ADD COLUMN` **不允许带 UNIQUE / PRIMARY KEY**。`join_code` 若直接写成 `ADD COLUMN join_code TEXT UNIQUE`，后端会**启动即崩**。
- **新增「表」时相反：写进 `_SCHEMA_SQL` 的 `CREATE TABLE IF NOT EXISTS`**（连同 `CREATE INDEX IF NOT EXISTS`，天然幂等，不需要 ALTER）。`t_question_kp` 与 `uq_qkp_primary`（部分唯一索引）即按此办理。
- 新表若带**物理外键指向 `t_question`**，须注意两点：① `_migrate_question_types()` 会 DROP/重建 `t_question`（该连接内先关 `foreign_keys`，末尾用 `PRAGMA foreign_key_check` 兜底）；② 所有删除路径必须**先删新表的行、再删题目**——连接默认 `foreign_keys = ON`，顺序反了会直接抛 FK 约束错误。

> ⚠️ **约束一目前有两处已知例外**（2026-10-08 核对代码发现）：`t_user.must_change_password` 与 `t_document.extract_started_at` / `extract_finished_at` 这三列**同时写在 `_SCHEMA_SQL` 和 `_migrate()` 两处**。后果分两种：
>
> - `extract_started_at` / `extract_finished_at`：两处都是**无约束的可空 `TEXT`**，**不产生分叉**，属无害例外。
> - `must_change_password`：`_SCHEMA_SQL` 里**带** `CHECK (must_change_password IN (0, 1))`，`_migrate()` 的 `ALTER TABLE` 里**不带**（SQLite 的 `ADD COLUMN` 本就不允许带 CHECK）。**这会产生真实的结构分叉**——新建库该列有 CHECK，旧库迁移来的没有；取值合法性目前靠应用层兜底，不影响功能。
> - 另一个分叉点是 `t_user.role` 的 CHECK：`_SCHEMA_SQL` 版本含 `admin`，旧库靠 `_migrate_admin_role()` **重建表**补齐——这一处是**有意的**，机制见 §2.1。
>
> 核对新库 / 旧库表结构时遇到上述差异，属已知情况，不是「迁移没跑」。

**历史课程不猜测学生成员关系**：迁移只回填教师，学生需通过加课码 / 邀请 / 申请重新加入。

**回滚方式**：恢复 `backend/backup/app.db.pre_*.bak`；或按外键反序 DROP 新增表、DROP 索引、DROP 新增列。

## 八、连接与并发（pragma）+ 备份

### 8.1 连接 pragma（`_connect()`）

| pragma | 值 | 作用域 | 说明 |
|---|---|---|---|
| `foreign_keys` | `ON` | 连接级 | 级联与 FK 约束；**所有**删除路径依赖它，顺序错了会直接抛错 |
| `busy_timeout` | `15000` ms | 连接级 | 写者互斥时**等待**而非立刻报 `database is locked`。默认 `sqlite3.connect` 的 `timeout=5s` 对批量写不够 |
| `journal_mode` | `WAL` | **库级、持久** | 读不阻塞写、写不阻塞读（只有写-写串行）。只在 `init_tables()` 末端设置一次 |

**为什么需要 WAL**：部署形态是「一个 uvicorn 进程 + 若干 CLI 脚本/评测」共写同一个
`app.db`；rollback journal 模式下**长读事务会挡住写者提交**，而 L2 引入的批量写入
（121 条向量 / 全量替换关联行 / ≤5000 行 BLOB 回填）又让写事务变长 —— 两头一夹就撞锁。
知识融合的 `apply` / `revoke` 同样把「写入映射 + `epoch+1` + 失效向量」压在一个事务里（见 §2.20），
是又一个长写事务来源。

- 失败**不抛异常**：网络盘等不支持 WAL 时退回流式 journal，正确性不受影响；
  但状态会被 `sql_db.pragma_status()` 保留（`requested` / `actual` / `error`），不静默丢弃。
- 回退开关：`SQLITE_JOURNAL_MODE=delete`、`SQLITE_BUSY_TIMEOUT=0`。
- **边车文件**：WAL 会产生 `app.db-wal` / `app.db-shm`（运行期文件，已加入 `.gitignore`）。
- ⚠️ **`backend/data/app.db` 被 git 跟踪**：WAL 下「主文件」可能不含最近提交，
  提交前应先让写事务结束/触发 checkpoint（最稳妥是出一份 `backup_to()` 快照再提交，
  或把该文件移出版本库）。这与 8.2 的裸拷问题是同一个坑。

### 8.2 备份必须走 `backup_to()`，不能裸拷文件

```python
fact = sql_db.backup_to("backup/sqlite_<ts>.db")   # 官方 backup API，WAL 安全
```

**为什么不能 `shutil.copy2(app.db)`**：WAL 模式下**最近提交可能还留在 `app.db-wal`** 里，
裸拷主文件会得到「**静默少数据**」的备份（不报错，事后才发现）；拷贝恰逢 checkpoint 时
还可能拿到内部不一致的快照。而回滚方式正是「恢复 `backend/backup/*.bak`」——
**备份静默失效 = 回滚路径静默失效**。

`backup_to()` 的行为：`sqlite3.Connection.backup` 取**写事务边界上的一致快照**（不阻塞写者），
并把备份文件 journal 复位为 `delete` 使其**单文件自包含**（无需连 `-wal` 一起拷）；
返回逐表行数便于与线上核对。`scripts/backup_migration.py` 已改走它。

> 启用 WAL **之前**生成的 `app.db.pre_*.bak` / `sqlite_*.db` 仍然有效
> （rollback journal 下主文件本身完整）；**之后**必须用 `backup_to()`。

### 1.3 统一设计原则

全部提示词遵循以下五条共同原则：

1. **结构化输出**：所有提示词都要求"严格只输出 JSON，不要 Markdown 代码块、不要解释文字"，且 system prompt 一律强调"只输出 JSON 格式"，保证程序可直接解析，无需二次清洗。
2. **证据约束**：关系抽取类提示词要求每条关系必须携带 `evidence`（原文短句，不得编造）与 `confidence`（0~1 置信度），实现抽取结果可溯源、可人工核验——这是达到赛题 70% 准确率要求的基础。
3. **宁缺毋滥**：明确"宁可少抽取，也不要臆造关系""证据不足时宁可不输出"，避免 LLM 幻觉污染知识图谱。
4. **负向示例（反例）驱动**：在易混淆边界处同时给出正例与反例（如"栈是一种操作受限的线性表"必须判 CONTAINS 而非 PRECEDES），比只给正例的纠偏效果显著更强（见第四节量化数据）。
5. **低温度采样**：凡涉及分类判断（关系类型、风险等级）的任务 temperature ≤ 0.15，抑制随机性；仅开放生成类（问答）放宽到 0.3。

## 二、P1 知识抽取提示词（核心，含完整迭代记录）

### 2.1 提示词设计目标

从课程文档分块中抽取"独立可学习的知识点"实体，并识别实体间的语义关系。这是全系统的技术核心，直接决定知识图谱质量与学习路径推荐的正确性。

**调用方式**：长文档先按 6000 tokens 分块（overlap 400 tokens），并发 4 路调用，逐块抽取后在代码层做实体归并与去重。

**System Prompt**：

```
你是一个精确的知识图谱构建助手。请只输出JSON格式的结果。
```

### 2.2 当前版本（v1.2，决策树版）完整原文

User Prompt（`{text}` 为分块后的课程文本）：

```
你是高校课程知识图谱构建专家。请从给定课程文本中抽取「可用于知识图谱与学习路径推荐」的知识点实体，并识别实体之间明确存在的语义关系。

## 核心原则
宁可少抽取，也不要臆造关系。禁止仅凭文本先后顺序、常识或名称相似性推断关系。
若对某条关系证据不足，直接不输出该关系。

## 一、实体要求
每个实体包含：
- name：知识点名称，简洁、规范、稳定
- category：只能是「概念」「定理」「公式」「方法」之一（无法归类时用「概念」）
- description：一句话描述该知识点在课程中的含义

实体粒度：
- 一个实体应是一个「独立可学习的知识点」，不要过度拆分，也不要堆砌冗余修饰。
- 同义词、英文缩写与中文全称属于同一知识点时，只保留一个规范名称。例如 CNN 与「卷积神经网络」合并为「卷积神经网络」。
- 不要抽取：人名、学校、公司、页码、章节标题本身、「本节」「上述方法」等指代词、普通名词、单纯例子名。

## 二、关系类型（仅限 4 种，英文大写，方向严格）
PRECEDES / CONTAINS / RELATED_TO / APPLIES_TO

## 三、关系判定必须按下述顺序（决策树）
对任意两个知识点，按顺序判断：

1. 上下位 / 整体-部分 / 类别-成员？ → CONTAINS（source 是 target 的上位概念/整体/类别，方向 source→target）
2. 否则，文本明确表达「学习 source 是理解 target 的必要前提」？ → PRECEDES（方向 source→target）
3. 否则，source 是方法/算法/技术，且文本明确说明其用于解决 target 代表的问题/对象？ → APPLIES_TO（方向 source→target，判定边界见第六节）
4. 否则，文本明确说明二者存在密切关联？ → RELATED_TO
5. 以上均不满足或证据不足 → 不输出关系

## 四、PRECEDES 只表示「学习依赖」，不表示「文本顺序」
只有文本明确表达以下语义才用 PRECEDES：学习 B 前须掌握 A；A 是理解 B 的基础；B 建立在 A 之上；掌握 A 后才能学 B。
典型触发词：「基础」「先修」「前提」「掌握…之后」「进一步学习」。

反例（以下禁止推断为 PRECEDES）：
- 「本章首先介绍线性表，然后介绍栈」→ 这是叙述顺序，不是学习依赖，不得输出「线性表 PRECEDES 栈」。
- 「卷积神经网络是神经网络的一种」→ 是包含关系，必须用「神经网络 CONTAINS 卷积神经网络」，不得用 PRECEDES。
- 「算法运行后生成结果」→ 时间先后，不是 PRECEDES。

## 五、CONTAINS 与 PRECEDES 的关键区分
- 「X 是 Y 的一种 / 特殊形式 / 变体 / 属于 Y」「Y 包含 X」→ Y CONTAINS X（绝不 PRECEDES）
  例：「栈是一种操作受限的线性表」→ 线性表 CONTAINS 栈
- 「要学习 X，必须先掌握 Y」→ Y PRECEDES X
  例：「要学习多态，必须先掌握继承」→ 继承 PRECEDES 多态

## 六、APPLIES_TO 与「实现 / 构成」关系的区分
只有当 source 被用于解决、处理、计算、优化或完成 target 所代表的问题/任务时，才能使用 APPLIES_TO。

以下表达不得自动视为 APPLIES_TO：
- 「X 通过 Y 实现」「X 由 Y 实现」「X 使用 Y 构成」「X 建立在 Y 之上」「X 包含 Y」「X 可以利用 Y 实现」

若文本表达的是「Y 是 X 的实现机制、组成部分或实现方式」，而当前关系集合中没有专门的 IMPLEMENTED_BY 关系：
- 不要强行转换成 APPLIES_TO；
- 根据上下文判断是否为 CONTAINS；
- 若无法确定，则不输出关系。

不要为了覆盖所有语义而强行映射到现有四类关系；证据不足时宁可不输出。

## 七、RELATED_TO 严格限制
仅用于「明确密切相关、但既非上下位、也非学习前置、也非应用」的情况，且文本有明确关联表述。
不要仅因两个概念出现在同一段就输出 RELATED_TO。

## 八、每条关系必须携带证据与置信度
- evidence：支持该关系的原文短句（必须来自输入文本，不得编造）
- confidence：0~1 的置信度，如实反映证据强弱，不确定就降低

## 九、输出约束
- source 与 target 必须都出现在 entities 中，且 source ≠ target
- 不重复输出相同 (source, type, target)；文本中因分块出现的重复段落，同一知识点/关系只输出一次
- type 只能是 PRECEDES / CONTAINS / RELATED_TO / APPLIES_TO
- 严格只输出 JSON，不要 Markdown 代码块，不要解释文字

## 十、输出格式
{
  "entities": [
    {"name": "实体名", "category": "概念", "description": "一句话描述"}
  ],
  "relations": [
    {"source": "源实体名", "target": "目标实体名", "type": "PRECEDES", "evidence": "原文证据", "confidence": 0.95}
  ]
}

## 课程文本
{text}

请只输出 JSON，不要包含任何其他内容。
```

### 2.3 版本迭代完整记录

抽取提示词共经历 **3 个版本**，版本号冻结于 `backend/eval_config.py`（`PROMPT_VERSION = "v1.2"`），每次变更均可追溯至对应 git 提交。

#### 版本 A（v1.0，初版 · commit 6755b9f）

简要规则版：定义 4 种关系类型（PRECEDES / CONTAINS / RELATED_TO / APPLIES_TO）+ 实体字段要求 + 基础输出约束（禁自环、禁重复、source/target 必须在实体列表中）。**无混淆排除规则、无 Few-shot 示例**。

#### 版本 B（v1.1，修复版 · commit 1c2ba24）

由测试报告的初测结果驱动（见 2.4 节量化闭环），核心改动：

1. **收窄 PRECEDES 定义**：删除原"识别到任何先后顺序关系必须用 PRECEDES"的宽泛表述，改为"只有存在明确'必须先掌握 A 才能学 B'的依赖时才用 PRECEDES"。
2. **新增关键排除规则**：`"X 是 Y 的一种 / 特殊形式 / 变体"` 一律判 `CONTAINS`（方向 Y→X），严禁 PRECEDES。
3. **新增 5 个 Few-shot 正反例**，其中示例 4、示例 5 专用于 CONTAINS / PRECEDES 边界区分：

   ```
   示例5（关键区分：CONTAINS vs PRECEDES，必须理解）：
     文本："栈是一种操作受限的线性表。"
     正确输出：{"source": "线性表", "target": "栈", "type": "CONTAINS"}
     错误输出：{"source": "线性表", "target": "栈", "type": "PRECEDES"}  ← 这是错的！"是一种"表示包含，不是先后学习顺序。

     文本："要学习多态，必须先掌握继承。"
     正确输出：{"source": "继承", "target": "多态", "type": "PRECEDES"}
   ```
4. **temperature 0.3 → 0.15**：关系类型判别需要稳定输出，降低采样随机性。

#### 版本 C（v1.2，当前版 · 决策树版 · commit f62bd23、d9516c2）

在 v1.1 基础上的结构性重构，改动四点：

1. **引入"关系判定决策树"**（第十节 2.2 原文第三节）：强制模型按 CONTAINS → PRECEDES → APPLIES_TO → RELATED_TO → 不输出的**固定顺序**依次判断，从"平行规则挑一条"变为"互斥的有序判定流程"，彻底消除规则间冲突。
2. **新增第六节**"APPLIES_TO 与实现/构成关系的区分"：修复复测中发现的新混淆模式——"X 由 Y 实现 / X 使用 Y 构成"被误判为 APPLIES_TO，明确此类表达不强行映射到现有四类关系。
3. **删除 v1.1 中"同一段文本中 PRECEDES 占比不应为 0，必须产出 PRECEDES"的强制条款**：该条款会诱导模型在没有真正前置关系时硬造 PRECEDES 边，与"宁缺毋滥"原则冲突。
4. **新增证据与置信度强制要求**（第八节）：每条关系必须携带 `evidence` 原文证据，实现抽取结果可溯源。

### 2.4 迭代量化效果（与《知识抽取准确率测试报告》对应）

| 阶段 | 版本 | temperature | 实体 F1 | 关系 F1（严格） | 关系 Recall（严格） |
|------|:----:|:-----------:|:-------:|:---------------:|:-------------------:|
| 初测 | A（v1.0） | 0.3 | 1.0000 | 0.4667 | 0.5000 |
| 复测 | B（v1.1） | 0.15 | 1.0000 | **0.9333** | **1.0000** |

- **主要错误根因**：初版规则 1（PRECEDES）标注"优先级最高"，导致"栈是一种操作受限的线性表"被系统性误判为 `线性表 PRECEDES 栈`（金标准为 `线性表 CONTAINS 栈`）。
- **修复收益**：仅修改提示词规则 + 2 个 Few-shot + 温度参数，关系抽取严格 F1 从 0.4667 提升至 0.9333（提升 100%），召回率从 0.5 提升至 1.0，**超过赛题 70% 准确率目标**。
- **v1.2 决策树版**在 v1.1 基础上进一步消除规则冲突与新发现的 APPLIES_TO 混淆模式，是最终冻结版本。

## 三、P2 前置关系补全提示词

### 3.1 用途与设计动机

文档文本中"必须先学 A 才能学 B"的显式表述往往是稀疏的，仅靠抽取会让 PRECEDES 边过少，学习路径推荐覆盖不足。本提示词在图谱构建完成后，将全部知识点清单（名称 + 类别 + 描述）一次性交给大模型，**基于教学逻辑常识**补全缺失的前置关系。

**可靠性保障**：补全的边带 `is_inferred=True` 标记与抽取边区分，教师可在图谱管理界面审核、一键回滚，不污染人工确认的知识。

**System Prompt**：

```
你是一名严谨的知识图谱构建助手，只输出 JSON。
```

### 3.2 完整原文

User Prompt（`{node_list}` 为每行一个"名称（类别）：描述"的知识点清单）：

```
你是一名教育领域知识图谱专家。下面是一个课程的知识点清单（名称 + 类别 + 一句话描述）：

{node_list}

请根据教学逻辑，补全这些知识点之间**缺失的「前置知识（PRECEDES）」关系**。

## 严格规则
- PRECEDES 方向为 source → target，表示「必须先掌握 source，才能学习 target」。
- **只有当两个知识点之间存在明确的先后学习依赖时，才输出 PRECEDES。**
- 以下情况**严禁**输出（这些不是前置关系）：
  - "X 是 Y 的一种 / 特殊形式 / 变体 / 组成部分"（这是包含关系 CONTAINS）
  - 两个知识点只是相关、并列、同层（这是相关关系 RELATED_TO，无先后顺序）
  - "X 用于 / 应用于 Y"（这是应用关系 APPLIES_TO）
  - 你不确定、或先后依赖不明显的
- 宁缺毋滥：只输出你**高度确信**的 PRECEDES 关系。
- source 与 target 必须是清单中**已有的知识点名称**，且不能相同。

## 输出格式（严格 JSON，只输出 JSON，不要输出任何解释）
{{
  "relations": [
    {{"source": "继承", "target": "多态"}}
  ]
}}

如果没有需要补充的关系，输出 {{"relations": []}}。
```

**设计要点**：负面清单中显式列出"包含 / 相关 / 应用"三类易混淆情形并指向正确的关系类型，与 P1 的决策树思想一致；示例取自教学场景中无争议的"继承 → 多态"，降低误补全率。

## 四、P3 智能问答提示词（RAG）

### 4.1 用途与检索链路

学生提问 → 问题 embedding（BAAI/bge-m3）→ 与知识点向量做余弦相似度 → 取 top-5 知识点作为上下文 → 填入 System Prompt → 大模型生成回答。向量检索失败时自动退回关键词检索。该设计对应赛题"利用 RAG 技术，让大模型在回答问题时优先参考课程知识图谱中的权威内容，避免幻觉"的要求。

### 4.2 完整原文

System Prompt（`{context}` 为检索到的知识点格式化内容；无相关知识时填"暂无相关课程知识"）：

```
你是一个课程学习助手。请基于提供的课程知识图谱内容回答学生的问题。

## 规则
1. 优先使用提供的知识内容回答问题
2. 如果知识库中没有相关信息，请诚实告知，不要编造
3. 回答要准确、简洁、易于理解
4. 如果合适，可以推荐相关的知识点供进一步学习

## 课程知识内容
{context}

请根据以上内容回答学生的问题。
```

User Prompt：学生原始问题原文，不做模板包装。

**设计要点**：
- 规则 1 + 规则 2 构成"优先引用 + 拒答诚实"双保险，直接针对 LLM 幻觉问题；拒绝编造是赛题明确关注点。
- 规则 4 引导模型在回答后推荐图谱中的相关知识点，将单次问答转化为学习导航入口，与"学习导航系统"定位呼应。
- temperature=0.3：问答需要一定语言流畅度，但仍保持较低温度以优先保证事实性。

### 4.3 测试验证

问答质量按《问答测试集.md》（`docs/问答测试集.md`）的测试集逐条验证，提交材料另含"智能问答的测试集与结果"。

## 五、P4 / P5 版本管理辅助提示词

系统内置基于 Git 的图谱版本管理功能，教师可查看每次提交对图谱的变更语义、评估回滚影响。以下两个提示词服务于该功能，体现"AI 深度融入工程全流程"的完整性。

### 5.1 P4 Git 提交语义分析

**System Prompt**：

```
你是一个精确的代码分析和版本管理助手。请只输出JSON格式。
```

**User Prompt 完整原文**（若有 diff 则在末尾追加 `## Diff 内容（截断）` 区块，最多 3000 字符）：

```
你是一个代码审查和版本管理专家。请分析以下 git commit：
```

## 八、方法论总结

1. **数据驱动的迭代闭环**：提示词迭代不是凭感觉改，而是"人工标注金标准 → P/R/F1 量化 → 定位系统性错误 → 修改规则/Few-shot/温度 → 复测验证"。v1.0 → v1.1 的修复使关系抽取严格 F1 提升 100%（0.4667 → 0.9333），单次闭环成本极低、收益极高。
2. **决策树优于平行规则**：v1.2 将"四条平行规则"重构为"互斥有序决策树"后，模型不再需要在规则间自由选择，类型混淆问题从机制上收敛。
3. **反例比正例更有效**：在易混淆边界（"X 是 Y 的一种"≠ 前置关系）显式给出"错误输出"标注的反例，纠偏效果远优于只给正确示例。
4. **证据强制 + 可回滚设计**：关系必须携带原文 evidence；推断边带 `is_inferred` 标记可回滚——从工程上兜底"LLM 一定会犯错"的前提，保证图谱质量上限不受模型错误影响。
5. **冻结纪律**：进入正式评测（Gold 标注）后提示词正文冻结不可修改（见 `docs/V1.1_冻结说明.md`），保证测试报告与提交版本严格对应；v1.3 迭代方向已在 `docs/知识抽取准确率评测计划.md` 中规划，留作后续优化。

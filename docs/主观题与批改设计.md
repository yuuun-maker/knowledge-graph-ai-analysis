# 主观题（填空/解答）与教师批改设计（Scope B）

> 交付物对应「题库题型扩展 + 主观题批改」。本文说明口径决策、数据模型、迁移方案、判分边界、接口与验证方式。
> 实现位置：`backend/app/services/question_service.py`（建题校验/投影/判分分发）、`backend/app/services/grading_service.py`（批改）、`backend/app/core/sql_database.py`（DDL + 迁移 + DAO）、`backend/app/api/grading.py`（接口）、`frontend-vue/src/views/TeacherView.vue`（题库表单 + 主观题批改 Tab）、`StudentView.vue`（填空/解答作答）。

---

## 一、口径决策（与需求方确认的最终方案）

1. **填空题 / 解答题统一按「主观题」处理**：建题时必须由教师给出**参考答案**（填空题每空一条，解答题整题一条）。
2. **学生的解答只作为作答记录落库**（`grade_status='PENDING'`、`score=0`、`is_correct=0` 均为占位），**未批改一律不判分**。
3. **只有教师批改后**才产生分数：`grade_status='GRADED'`、`grade_source='TEACHER'`，并按 `score >= 60`（`GRADE_PASS_SCORE`）折算对/错。
4. **自动组卷/智能推荐默认不硬插入这两个题型**：不参与题型均衡与配额补齐，只有显式指定 `q_type=FILL/ESSAY` 时才出现。
5. **批改采用「就地更新」**：直接 UPDATE 同一条 `t_answer_record`（不留批改历史版本，重批即覆盖）。
6. **参考答案在下发时机上后置**：主观题提交后**不下发**参考答案与解析，教师批改后才可见（主观题的「解答」本身是教学资源，提交即给会削弱反思与批改意义）。

**为什么不做 LLM 自动判分**：主观题自动评分需要 rubric + 一致性校准 + 成本控制，并且「AI 给分可信度」是产品与答辩上的高风险点。当前方案用「教师批改」替代，等于把风险换成了可靠的人工流程；判分算法仅作为**可选**的批改辅助（本次未实现）。

## 二、题型与判分边界

| 题型 | 代码 | 判分方式 | 存储形态 |
|------|------|----------|----------|
| 单选题 | `SINGLE` | 选项键归一化后严格相等（提交即判） | `options=[{key,text}]`，`answer="A"` |
| 多选题 | `MULTI` | 键集合严格相等（顺序无关） | `answer=["A","C"]` |
| 判断题 | `JUDGE` | 布尔归一化（对/正确/true/T/1 等价） | `answer="true"` |
| **填空题** | `FILL` | **教师批改（不自动判分）** | `options=[{key,label,hint,score,answer}]`（每空参考答案），`answer=[参考答案数组]` |
| **解答题** | `ESSAY` | **教师批改（不自动判分）** | `options=[]`，`answer="参考答案正文"` |

分组常量（应用层唯一来源，`core/sql_database.py`）：
```python
QUESTION_TYPES     = ("SINGLE", "MULTI", "JUDGE", "FILL", "ESSAY")
AUTO_GRADE_TYPES   = ("SINGLE", "MULTI", "JUDGE")     # 提交即判分
MANUAL_GRADE_TYPES = ("FILL", "ESSAY")                # 提交只落库，教师批改
ANSWER_GRADE_STATUS = ("PENDING", "GRADED")
```

**建题校验（后端强制）**
- 填空题：≥1 个空位（≤20）、每空参考答案必填（≤200 字符）、空位编号不重复、分值 0~100；
- 解答题：参考答案必填（≤4000 字符）；
- 校验失败统一返回 `code=1001`，前端也做同口径的前置提示。

## 三、状态机与统计口径

```
客观题提交        → GRADED / grade_source='AUTO'   / score ∈ {0,100}
主观题提交        → PENDING / grade_source='AUTO'  / score=0, is_correct=0（占位，不代表答错）
教师批改（单/批量）→ GRADED / grade_source='TEACHER' / score ∈ [0,100]
                    is_correct = (score >= GRADE_PASS_SCORE=60)
重批              → 同一行覆盖（含评语与批改痕迹）
```

**凡涉及「对错」的统计一律只看 `grade_status='GRADED'`**，否则「交了但老师还没批」会被当成答错：

| 位置 | 口径 |
|------|------|
| `sql_database.question_answer_stats()` | 默认 `graded_only=True`（保护推荐器「区分度」信号） |
| `PracticeService.records() / stats()` | 返回 `graded_count` / `pending_count`，正确率只按已批改算 |
| `PracticeService.wrong_book()` | `include_pending=False`：未批改不进错题本 |
| `QuestionService.stats()` | `pending_count` + `grading` 汇总（教师端角标） |
| `question_recommender.kp_mastery()` | 只喂已批改记录；**已批改的得分按 `score/100` 参与加权**（支持部分分） |
| `question_recommender` 逐题统计 | 含待批改记录（影响新颖度/遗忘到期），但 `last_is_correct=None`：既不当作对也不当作错 |

## 四、数据模型与迁移

**题目表 `t_question`**：`q_type` 的 CHECK 由 3 类扩到 5 类。
SQLite 无法修改 CHECK，因此 `_migrate_question_types()` **重建表**（幂等）：

```
幂等守卫（sqlite_master.sql 中是否已含 FILL）
  → 独立连接 + PRAGMA foreign_keys=OFF（t_question 是两张子表的父表；且该 PRAGMA 在事务内是空操作）
  → BEGIN → 记录旧 AUTOINCREMENT 续号 → 清理残留新表 → 建新表 → 显式列名 INSERT…SELECT
  → 行数校验 → DROP 旧表 → RENAME → 重建 3 个索引
  → 续号取 max(旧续号, 当前最大 id)（历史删过题时旧续号更大，单取 max(id) 会复用已删除 id）
  → PRAGMA foreign_key_check 必须为空 → COMMIT（任一步失败即 ROLLBACK）
```
> 建表 DDL 抽成模块常量 `_T_QUESTION_DDL`，`_SCHEMA_SQL` 与迁移共用，避免两份 DDL 漂移。

**作答表 `t_answer_record`**：只 `ADD COLUMN`（不重建，`grade_source` 已含 `TEACHER`）：
`grade_status`（默认 `'GRADED'`，历史行零变化）、`graded_by`、`graded_at`、`comment`。

**新库 / 旧库差异（已知不对称）**：新库由 `_SCHEMA_SQL` 建出带 CHECK 的 `grade_status`；旧库 ADD COLUMN 不能带 CHECK，由应用层白名单兜底。

## 五、接口

| 方法与路径 | 说明 |
|-----------|------|
| `GET /api/v1/grading/pending` | 待批改列表（含题面、**参考答案**、学生解答、学生姓名；先交先批；可按文档/知识点/学生过滤 + 分页） |
| `POST /api/v1/grading/{record_id}` | 单题批改：`{score: 0~100, comment?}`；客观题 → `4001`；非本课程教师 → `4003` |
| `POST /api/v1/grading/batch` | 批量批改（同一分数与评语，≤200 条）；逐条跳过无权限/客观题/不存在并返回原因 |
| `GET /api/v1/grading/summary` | 批改进度：`pending / graded / manual_total / auto_total / avg_score` |

权限：接口层 `require_teacher`，服务层再做「课程归属校验」（越权 4003）；学生无法批改自己。
**教师端待批改接口带参考答案属于预期行为；学生端接口（`_public_view`）永不含答案。**

## 六、前端

**教师端**
- 建题表单三分支：选择题（选项编辑器）/ **填空题（空位编辑器：参考答案 + 提示 + 分值）** / **解答题（参考答案文本域）**；
- 题库总览新增「填空题 / 解答题 / **待批改**」KPI（待批改 > 0 高亮）；
- 新增「主观题批改」Tab：批改进度卡 + 待批改表格（左学生解答、右参考答案；填空按空逐行对照）+ 逐题给分（弹窗可填评语）+ 勾选批量给分。

**学生端**
- 填空题多空输入（占位符显示空位提示）、解答题多行文本域；
- 提交后结果区显示 **「已提交，等待教师批改」**（中性配色），批改后显示得分、正确答案、教师评语与解析；
- 练习统计/错题本不会因未批改而失真（文案与口径见第三节）。

## 八、已知边界与后续可选项

1. **批改不留历史**：重批直接覆盖（按既定方案）。若后续需要审计/申诉，可加 `t_answer_grade_log` 追加式日志表，不改现有读写路径。
2. **不做自动判分**：填空题的「答案等价判定」（数值/单位/别名/语义）与解答题的「采分点命中」都**未实现**，仅作为后续可选的「批改辅助建议分」——即便实现，也只作为教师界面上的提示，**不自动写库**。
3. **填空题分值只是提示**：当前批改由教师直接给总分（0~100），每空 `score` 仅用于批改时参考；若将来要做「按空给分」，需要扩展批改接口为逐空打分。
4. **试卷/作业场景未覆盖**：当前是「练习 + 批改」，没有作业截止时间、批量发布、成绩单导出。
5. **未批改主观题不计入掌握度**：学生若长期不做主观题，掌握度完全由客观题决定（这是刻意的：未知不等于错）。

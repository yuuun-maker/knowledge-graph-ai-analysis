# 协作与图谱共享方案（待团队决策）

> 背景：本项目多人协作，但"**关系库 / 上传文档 / 知识图谱**"三者的共享方式不一致，已经在实际开发中造成数据错位与功能不可用。本文给出**实测证据、影响评估与可选方案**，供团队拍板。
>
> 相关实现：`backend/seed_practice_data.py`（演示数据种子脚本）、`docs/题库功能说明.md` 第 9.7/9.8 节。

---

## 一、已经发生的现象

1. **课程 63「数据结构 · 树与二叉树」的图谱不在本机**：本机 Neo4j 中该课程的知识点数为 **0**，
   而 `app.db` 里有 24 条 `t_kp_embedding`、6 道题、12 条学习记录都指向它 → 只能生成"占位题"
   （题干含原始 `kp_id`、类别是默认值），无法演示真题。
2. **本机 Neo4j 里有两份来历不同的图谱**：`course 36 / doc 95`（23 个知识点）与
   `course 65 / doc 101`（40 个知识点），二者与 `app.db` 的对应关系都对不上。
3. **`app.db` 里的文档路径是别人机器的绝对路径**：如
   `F:\com\knowledge-graph-ai-analysis\backend\data\uploads\63\94_第五章 树与二叉树（讲义）.txt`，
   本机 `os.path.exists()` 为 False（文件其实在仓库里，见第二节）。

---

## 二、根因：三者共享方式不一致（关键）

| 数据 | 是否入 git | 实测证据 | 后果 |
|------|:---:|------|------|
| `backend/data/app.db`（课程 / 用户 / 密码哈希 / 文档记录 / 题目 / 作答 / 学习记录 / 向量） | ✅ 入 | 28 个历史版本 blob，累计 **83.9 MB**，HEAD 单份 4.3 MB | 各人**本地演示数据互相覆盖**；二进制无法合并（最后提交者获胜）；含全部账号密码哈希 |
| `backend/data/uploads/**` | ✅ 入 | `git ls-files` 共 **21 个文件**（含课程 63/64 的讲义） | 文档能共享，但库里的 `file_path` 指向**对方机器的绝对路径**，本机判定为不存在 |
| **Neo4j 图谱**（`kp_id` ↔ 知识点 / 关系） | ❌ **不入**（各人本地实例，`.env` 各一份） | 本机实测：`course 65/doc101=40`、`course 36/doc95=23`、`course 63/doc94=0`；关系只有 `RELATED_TO 18`、`APPLIES_TO 2`，**无 `PRECEDES`** | `app.db` 里的 `kp_id` 在别人机器上**大面积悬空**；知识抽取结果无法共享 |

**一句话总结**：`app.db` 与文档进了仓库，只有"图谱"留在各人电脑里 —— 于是"课程是你的、知识点是我的"。

## 三、取证方法与结论（可复现）

对 `app.db` 逐个提交做只读取证（从 git 取 blob → 临时文件 → SQLite 查询），得到课程集合的时间线：

| 提交时间 | 提交人 | 该版本 `app.db` 中的课程 | 用户数 |
|---|---|---|---|
| 2026-09-12 18:46 `0cd25c6` | zane-a-wq | [5, 9, 10, 11, 12, 30, 31] —— **无 63** | 5 |
| **2026-09-13 22:29 `269cd3d`** | **zane-a-wq** | [5, 9, 10, 11, 12, 30, 31, **63, 64**] | **7（新增 109 `demo_teacher` / 110 `demo_student`）** |
| 2026-09-11 14:38 `8d2d1bd` | yuuun-maker | 含 **36**「计算机组成原理」（当时 doc95 = 《计算机组成原理试题5答案.pdf》） | 9 |

结论：
- **课程 63/64 是协作者 zane-a-wq 的本地演示数据**，由账号 `demo_teacher(109)` 于 2026-09-12 21:02 创建，
  随 `269cd3d` 提交进仓库；其图谱只存在于对方的 Neo4j 中。
- 本机 Neo4j 的 `course 36/doc 95` 是 **yuuun-maker 时期**的遗留图谱；而本机 `app.db` 现在把 `doc 95`
  分配给了课程 64 的《第二章 进程与线程（讲义）.txt》→ **doc_id 两边错位**。
- `demo_teacher / demo_student` 是**团队约定的演示账号**（前端 `LoginView.vue` 硬编码，密码
  `demo123456`），因此课程 63/64 属于"有意的演示数据"，不是无主垃圾。

## 四、影响评估：协作者拿到 `app.db` 后能用什么？

**先说结论：文件层面完全能访问（git 完整保存二进制），但图谱相关能力会失效。**
把 `NEO4J_URI` 指向一个不存在的端口（模拟"没有可用图库"）后实测：

| 能力 | 无图谱时 | 说明 |
|------|:---:|------|
| 出题 `GET /api/v1/practice/questions` | ✅ 可用 | 纯 SQLite |
| 我的练习统计 `GET /practice/stats` | ✅ 可用 | 纯 SQLite |
| 错题本 `GET /practice/wrong-book` | ⚠️ 可用但降级 | 题目能返回，但 `kp_name = None`（知识点名称要从 Neo4j 取） |
| 教师教学监测 `GET /teacher/students/progress` | ❌ **500** | `teacher_service.py` 中 `PathRecommender.recommend_next` 未被 try/except 包裹 |
| 学生进度 `GET /learning/progress` | ❌ 预计 500 | `learning.py` 中的 `db.query` 同样未捕获（**按代码判读，未实测**） |
| 图谱浏览 `GET /graph/{cid}` | ⚠️ 友好报错 | `graph.py` 捕获异常 → 返回 `code 3000 图谱查询失败` |
| 学习路径 / 推荐 / 知识点跳转 | ❌ 不可用 | 依赖图谱 |
| 登录 | ✅ 可用 | 密码哈希就在 `app.db` 里（这也是**凭据外泄**问题） |

> 若对方本机有 Neo4j 但**没有该课程的节点**（更常见），不报错而是静默降级：
> 知识点总数 0、进度 0%、推荐为空、知识点名称显示为原始 `kp_id` —— 比报错更难排查。

**提交 `app.db` 的其他代价（实测）**

| 项目 | 数值 |
|------|------|
| `app.db` 历史版本 blob 数 / 累计体积 | **28 个 / 83.9 MB**（HEAD 单份 4.3 MB） |
| 仓库 pack 体积 | **52.41 MiB**（绝大部分来自 `app.db` 历史） |
| 合并能力 | 二进制无法合并，**最后提交者获胜**（互相覆盖） |
| 安全 | 含全部账号 PBKDF2 哈希（含真实协作者账号） |

## 五、可选方案对比

| 方案 | 做法 | 成本 | 收益 | 风险 |
|------|------|:---:|------|------|
| **① 统一共享 Neo4j**（目标态） | 团队统一用 AuraDB 云实例或内网 Neo4j，URI/账号写进团队配置（`.env` 不入库） | 中（需一人申请/维护实例） | 图谱天然一致；所有图谱功能跨人可用 | 单一实例被改坏影响全员；网络依赖 |
| **② 图谱导出 JSON 随仓库走**（最低成本，可立即落地） | 新增 `export_graph_json.py` 导出某课程的 KnowledgePoint + 关系为 `backup/neo4j_<course>_<时间>.json`；别人用 `seed_practice_data.py --kp-json <文件>` 复现真题 | 低（约 100 行脚本） | 无需服务器；可版本化、可追溯；与现有 `backup/neo4j_*.json` 格式一致 | 图谱变大后文件较大；更新需重新导出（可接受） |
| **③ 维持现状** | 各人本地建图，互不共享 | 0 | — | **已证明不可行**：跨人演示/联调必然错位（本文件第一节即为此） |

**推荐组合**：**② 先落地（本周即可用） + ① 作为目标态（下阶段）**。

## 六、配套动作：让 `app.db` 与 `uploads` 退出 git

> 需要与 3 位协作者约定后**一次性完成**，避免"我删了、你又提交"的拉锯。

```bash
# 1) 先让所有人保留自己的本地数据（这份文件退出索引后，各人本地文件仍在）
# 2) 由一人执行：
git rm --cached backend/data/app.db
git rm -r --cached backend/data/uploads
# 3) 追加 .gitignore：
#    backend/data/app.db
#    backend/data/uploads/
# 4) 提交并在群里公告：以后数据库由各人本地生成
#    python seed_practice_data.py --course-id <你的演示课程> [--kp-json <图谱导出>]
```

注意事项：
- 退出索引**不会删除**任何人本地已有的 `app.db`；但**历史提交里的数据仍在**（如需彻底清除要 `filter-repo`，成本高，建议只做"停止继续提交"）。
- 退出后建议保留一份**共享种子数据**（例如由 `seed_practice_data.py` + 图谱 JSON 生成），保证新人 clone 后一条命令即可演示。

## 附一：现有脚本与参数（已交付）

`backend/seed_practice_data.py`（演示数据种子脚本，中文注释）：

| 参数 | 作用 |
|------|------|
| `--course-id <id>` | 目标课程（默认 63） |
| `--per-kp N` / `--max-kp N` | 每个知识点出题数（≤5）／参与造题的知识点数上限 |
| `--students N` / `--days N` / `--coverage 0-1` | 演示学生数、作答时间回溯跨度、作答覆盖率 |
| `--kp-json <文件>` | **从图谱导出 JSON 读知识点**（Neo4j 不可用时的推荐做法，格式兼容 `backend/backup/neo4j_*.json`） |
| `--offline-kp` | 只用 SQLite 已有 `kp_id` 兜底（题干会退化为 `kp_id`，仅用于打通流程） |
| `--clean-only` | 只清理本脚本写入的数据（撤销演示数据；与 `--keep` 互斥） |
| `--keep` / `--dry-run` / `--seed N` | 追加不清理 ／ 只打印计划 ／ 固定随机种子（结果可复现） |

安全边界：只操作 `source='IMPORT'` 的题与 `source='SYSTEM'` 的学习标记；**教师手工题与
`MANUAL` 学生自评记录永不触碰**（曾发生过 upsert 覆盖 MANUAL 记录的事故，已修复并写入文档）。
